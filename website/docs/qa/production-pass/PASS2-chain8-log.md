# Pass 2, chain 8: walls, renders, moderation, blog reject

The remainder of Track C, run 2026-08-31 on records created in-session.

## Wall creation, editor and render

**Creation is capped, and the cap arrives too late.** The venue is on
`venue_standard` with 3 of 3 saved walls used. `/venue-portal/walls` shows a
"Upgrade to add more than 3 walls" notice, but "+ New Wall" is **not disabled**:
it opens the form, lets you choose a preset, name the wall and press Create wall,
and only then does `POST /api/walls` return
`402 {"error":"You've used all 3 saved walls on your plan.","reason":"saved_walls_cap","tier":"venue_standard","cap":3}`.
The body carries reason, tier and cap exactly as the inventory describes; the
front end renders it as one plain inline line, with no amber panel and no
`/pricing` link.

The preset picker is correct: choosing "Gallery charcoal" set the colour to
`#2a2a2a` **and** the dimensions to 400×260 in one action, with the colour wheel
still editable afterwards. W/H carry `min=50 max=1000`.

**The editor and the render pipeline both work.** Opening an existing wall gave
the full-bleed editor with a works rail (My 21 / Saved 0 / All 260, "Showing 20 of
21" with a pager), a 2D/3D toggle, the wall config bar, and a live save chip.
Clicking *Mt. Fitz Roy* placed it and opened the item toolbar with a size chip
(36×24") and the five frame styles.

Render returned an image in about 4 seconds and the modal read "Used 1 render
unit / 1 item · 4.1s". The quota decremented visibly to "1 of 5 artworks today",
and both ledgers landed:

- `wall_renders` `45403984-…`, `cost_units: 1`, `kind: standard`, `layout_hash`
  set, `output_path` a per-user `.webp`, `kept: false`.
- `visualizer_usage` id 27, `action: render_standard`, `cost_units: 1`,
  `day_bucket: 2026-08-31`, `month_bucket: 2026-08`, metadata carrying `wall_id`,
  `layout_id`, `work_ids` and `item_count`.

So the quota model is real and append-only, exactly as column 2 claimed. Note
`provider` is NULL and `kind` is `standard`: this render is composited, not
generated by an AI provider.

## Message moderation

This is the one refusal on the whole site that tells the user what happened.
Sending "Email me at qa-test-probe@example.com or call 07700 900123 so we can
settle this off Wallplace" returned `POST /api/messages 400 {"error":"Message
contains blocked content"}`, and the thread rendered **"Message contains blocked
content"** above the Send button.

Verified nothing was written: no `messages` row, and no `moderation_queue` or
`conversation_reports` row either. So a blocked attempt to take a deal
off-platform leaves no trace an admin can see. The `/admin/moderation` Messages
filter has nothing to show for it.

Incidentally the thread rendered every in-thread card correctly: the purchase
offer card with image, size and medium, the counter card, the placement request
card with a "⊘ Cancelled" pill, and "Awaiting response…" on the sender's own open
offer.

## Blog submit and reject

**Submit for review fails silently below 200 characters.** A 120-character body
produced `PATCH /api/blogs/[id] 422 {"error":"Not ready for review","issues":
["Body needs at least 200 characters before submitting."]}`. The API's message is
excellent. The UI shows none of it: the button returns to rest and the status
stays "draft". On `/artist-portal/blogs/new` the same click saves the draft
(POST 200) and then fails the review PATCH, so the artist lands on the edit page
believing they submitted. Padding the body past 200 characters moved it to
`pending_review` first time.

**The rejection reason reaches the artist by no route at all.** Rejecting from
`/admin/blogs` prompts "Reason (emailed to the author):" — note *emailed*, not
"visible to the author" as the inventory says, and the difference is the finding.
The reason is stored **only** in `admin_audit_log` (`blog.reject`, full text in
context); `blogs` has no rejection-reason column. The artist's portal shows a bare
"Rejected" badge with no explanation. And the `artist_blog_rejected` email that
carried it was `skipped_throttled`, so on this occasion nothing reached them.

The status flip itself is correct: `blogs.status` went to `rejected`, the row left
the admin Pending tab, and `moderation.read` audit rows bracket the action.
