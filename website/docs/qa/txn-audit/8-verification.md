## The three tensions resolved

### Tension 1: the dunning email that exists, was never sent, and burns its key

All three reports are right about different layers, and together they resolve cleanly.

**The code (report 2 is right).** The SaaS dunning branch is live in the current code at route.ts:1599-1650: on every `invoice.payment_failed` it writes past_due, then sends `subscription_payment_failed` keyed `payment_failed:{invoiceId}:{attempt_count}`, one email per Stripe attempt, in `orders_and_payouts`, which is `criticalAlwaysSend: true` (categories.ts:34) and therefore bypasses suppressions, preferences, vacation mode and throttles. No user setting can stop it.

**Production (report 5 is right, re-verified live).** Zero email_events rows have ever existed for that template, by key or by name, while 5 `subscription_cancelled` emails went to 4 users between 2026-05-17 and 2026-08-17. Decisive detail from git: the dunning email and the cancellation email were introduced in the SAME commit (402ea1a, 2026-04-24). The deploy that demonstrably sent cancellation emails therefore contained the dunning branch too. So "the code was not deployed yet" is ruled out.

**What zero rows means.** Every downstream failure mode leaves a row: a provider failure writes `failed`, a preference skip writes `skipped_*`, a missing API key writes `skipped_no_api_key`, a dry run writes `dry_run`. Zero rows means `sendEmail` was never invoked: the branch never executed with a resolvable profile. Since the cancellation branch resolved the same profiles by the same customer ids and sent successfully, the failure sits UPSTREAM of the handler: `invoice.payment_failed` (and `customer.subscription.trial_will_end`, also zero rows ever) never reached the endpoint. Either the Stripe webhook endpoint's enabled-events list omits them, or the five cancellations happened without a dunning cycle (manual dashboard cancellations would also produce exactly this signature). The stripe_webhook_events table (populated only since the 2026-08-28 deploy) contains no `invoice.payment_failed` yet, so delivery of that event type remains unproven in either direction.

**Report 4's key-burn is NOT the explanation.** The burnt-idempotency-key mechanism (a prior failed row blocking the claim) presupposes a first attempt that wrote a row. There are no rows. The key-burn finding is real and stands, but as a forward-looking risk: the first dunning attempt that fails at the provider will be permanently unresendable.

**Definitive account:** the dunning path is live-but-never-triggered. The trigger failure is upstream of the code, at the Stripe endpoint's event subscription or in how those five subscriptions actually ended. Action for the owner: open the Stripe dashboard, check the webhook endpoint's enabled events for `invoice.payment_failed` and `customer.subscription.trial_will_end`, and check how the five cancelled subscriptions ended (dunning exhaustion versus manual cancellation). Redeploying alone, report 5's suggested fix, may not be sufficient.

The outer wrapper exists and works: `handleWebhookEvent` is called inside try/catch at route.ts:105-110, a throw becomes a 500, and any response >= 500 deletes the claim at 117-125. F1 survives it because the cart branch catches first.

### Tension 3: what actually happens today on a chargeback and on a dashboard refund

**(a) `charge.dispute.created`.** Signature verified (route.ts:62-80), event id claimed into stripe_webhook_events (:86-101), then no branch matches any `charge.dispute.*` type (grep: zero), so the event falls to the default `{ received: true }` 200 at :1946 and the claim is kept: the event is permanently marked processed. Nothing else happens in the platform. No order write (the `order.disputed` lifecycle vocabulary from migration 105 is never fed), no bell, no email, no admin alert; the internal disputes system (src/app/api/disputes) is buyer-versus-artist messaging and never sees Stripe disputes. Meanwhile Stripe debits the platform balance for the disputed amount plus the dispute fee. The order keeps its status, so: pending legs inside the 14-day hold are paid out on schedule by the next 08:00 sweep, because processPendingTransfers rescues only orders in cancelled/refunded (stripe-connect.ts:349); already-paid legs, including the immediate legs of every collection or collect_venue sale (which have no hold at all), are never reversed. `charge.dispute.closed` is equally unhandled, so a won dispute never reconciles and a lost one never marks the order. With no alert, the 7-21 day evidence window lapses unnoticed and the dispute is lost by default. The code's own comment calls the 14-day hold "the platform's only chargeback buffer" (orders/route.ts:188-190); nothing connects a dispute to it, and immediate-release sales have no buffer at all.

**(b) A dashboard refund.** Stripe fires `charge.refunded` (plus refund lifecycle events). None is handled; the event is claimed and answered 200, which the webhook's own test suite pins by using charge.refunded as its example of a benign fall-through. In the database nothing changes: order status and revenue columns stay as they were, no restock (restock_work runs only inside refunds/process), refund_requests untouched, no emails or bells to anyone. Consequences: still-pending artist and venue legs execute on the next sweep for a sale the buyer has been repaid on, and paid legs are never reversed, so the platform is out the refund while still paying both recipients. If an operator also reverses the transfers by hand in the dashboard, the platform actively undoes them: `transfer.reversed` IS handled (route.ts:1867-1876) but writes `failed`, a retryable state; the next morning's sweep re-selects the row (stripe-connect.ts:324), the order still reads delivered so no rescue applies (:349), executeTransfer accepts failed rows (:143) with no already-transferred guard, and the Stripe idempotency key `transfer:{ledgerId}` (:155) has expired after ~24 hours, so a brand-new transfer for the FULL original leg is created and the ledger overwrites itself to a clean paid. The only shapes that stick are marking the order refunded in-app first (the sweep then cancels the rows) or hand-editing the ledger. The in-app path (/api/refunds/process) does everything correctly, reversal-first with abort-on-failure, but only for requests raised in-app, and request/route.ts:110-121 blocks a second request once any non-rejected one exists, which funnels follow-up adjustments to the dashboard, the exact surface with no handler.

The four reports describe this identically in substance and differ only in severity labels (R1 filed the chargeback gap P2, R3 filed it CRITICAL). Given that collection-sale legs release immediately and that R3.1 converts even a correct manual cleanup into a double payment, the synthesis should carry both dispute handling and external-refund handling at R3's severity, and treat R3.1 (the transfer.reversed handler writing `failed` instead of a terminal `reversed`) as the single highest-priority one-line fix in the money-out domain.
